Field guide · part 1

How a Ray cluster works

Ray lets one ordinary Python program use the CPUs and memory of many computers as if they were one. You mark a function with @ray.remote, call it with .remote(), and Ray decides which machine runs it. You get back a ticket (an ObjectRef) and later swap it for the answer with ray.get().

Head node

The boss. It runs the GCS, the cluster's address book, which tracks every node, job, and actor. It also hosts the dashboard. Ours is minipc.

Worker nodes

Each one runs a raylet, a local manager that starts Python worker processes and schedules tasks onto the machine's CPUs. Each also keeps a shared-memory object store for results.

Driver

The script you run, like pi_job.py. It connects with ray.init(address=…), sends out work, and collects results. It can run on any machine that can reach the head.

Results travel between machines through the object stores, not through shared folders. That is why big data should go in through ray.put() or task arguments. A file path on one PC means nothing on another.

Field guide · part 3

Getting it online, safely

Never port-forward Ray to the internet. By default Ray has no passwords. Anyone who can reach port or can run any code they like on every machine in the cluster. Attackers have scanned for exposed Ray clusters in real attacks (known as "ShadowRay", CVE-2023-48022).

The safe way is a private mesh VPN. Every machine gets a private address that only your own devices can reach, and it works through home routers with no port forwarding. Tailscale is the easiest option. ZeroTier, Headscale (self-hosted Tailscale) and plain WireGuard also work.

  1. Install Tailscale on every machine that will be in the cluster. Sign them all into one tailnet. Chris invites Austin as a user. Node "sharing" between two separate tailnets is one-way, and Ray needs machines to connect in both directions.
  2. Note each machine's 100.x.y.z address with tailscale ip -4.
  3. Restart the head so it announces its Tailscale address: 
    ray stop
ray start --head  \
  --node-ip-address=<minipc 100.x IP> \
  --dashboard-host=<minipc 100.x IP>
  4. On every worker, including the home ones, join using its own Tailscale IP: 
    ray stop
ray start --address=<minipc 100.x IP> \
  --node-ip-address=<this machine's 100.x IP>
  5. In the Tailscale admin console, add an access rule so only tagged Ray machines can talk to each other. This stops a phone or laptop on the tailnet from reaching the cluster.
Match versions everywhere. Every machine needs the same Ray version (2.59.0) and the same Python minor version. Use Linux. Windows PCs can join through WSL2 (see part 6).
Field guide · part 4

Austin's cluster plus Chris's

One Ray cluster has exactly one head node, and Ray cannot merge two clusters that each have a head. You have two good options:

Option A · one big cluster

Austin's PCs join as workers

Austin's machines run ray start --address=<minipc> over Tailscale. One dashboard and one pool of CPUs. The catch: work can land on any machine, and data moves over the internet, which is far slower than the LAN.

Option B · two clusters

Each runs a head, and you send jobs to each other

Austin builds his own cluster. You each submit jobs to the other's head over Tailscale with ray job submit. Each cluster stays fast and fails on its own. This is the simpler and sturdier starting point.

Sending a job to the other cluster (the code folder is uploaded, so no shared drive is needed):

ray job submit --address http://<other head 100.x IP> \
  --working-dir . -- python pi_job.py

With Option A, you can still keep work local by tagging machines with a custom resource and asking for it:

# on Austin's machines
ray start --address=<minipc> --resources='{"austin": 100}'

# in code: only runs where the "austin" resource exists
@ray.remote(resources={"austin": 1})
def crunch(x): ...

What suits the internet: chunky, CPU-heavy tasks with small inputs and outputs, like the pi test, simulations, and parameter sweeps. What suits the LAN only: jobs that pass big arrays or datasets between machines.

Field guide · part 5

Austin: building your own cluster

  1. On each Linux machine: python3 -m venv ~/.venvs/ray && ~/.venvs/ray/bin/pip install "ray[default]==2.59.0"
  2. Pick your strongest always-on box as head: ray start --head --port=
  3. On the others: ray start --address=<head IP>
  4. Check it: ray status, then open http://<head IP> for the dashboard.
  5. Run a test job, for example Chris's pi_job.py with the address changed, and watch it on the dashboard's Jobs page.
  6. Then add Tailscale (part 3) and choose Option A or B (part 4).
Field guide · part 6

Adding Windows PCs on Austin's side

Ray on plain Windows only works as a single computer: a Windows PC can't join a multi-node cluster natively. The way in is WSL2, a real Ubuntu Linux that runs inside Windows 10 or 11. Ray runs inside Ubuntu, and the PC joins as an ordinary Linux worker. Keep the head on a real Linux machine and use Windows PCs as workers.

  1. Install Ubuntu. In PowerShell as administrator, run the command below, then reboot and create a Linux username when Ubuntu opens. 
    wsl --install -d Ubuntu-24.04
  2. Install Ray inside Ubuntu. Use the same Ray version as everyone else, and check that python3 -V matches the cluster's Python minor version. 
    sudo apt update && sudo apt install -y python3-venv
python3 -m venv ~/.venvs/ray
~/.venvs/ray/bin/pip install "ray[default]==2.59.0"
  3. Install Tailscale inside Ubuntu, not only on Windows. WSL normally hides behind a private address that other machines can't reach. Tailscale gives the Linux side its own 100.x address that every other node can reach. 
    curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale ip -4
    If it complains about systemd, put [boot] and systemd=true on two lines in /etc/wsl.conf, run wsl --shutdown in PowerShell, and reopen Ubuntu.
  4. Join the cluster from Ubuntu, using the WSL Tailscale IP: 
    ~/.venvs/ray/bin/ray start --address=<head 100.x IP> \
  --node-ip-address=$(tailscale ip -4)
  5. Give WSL enough of the PC. WSL gets only half the RAM by default. Create C:\Users\<you>\.wslconfig, then run wsl --shutdown: 
    [wsl2]
memory=12GB
processors=8
  6. Make it rejoin at login. In Task Scheduler, create a task that runs at logon with program wsl.exe and these arguments. --block keeps Ray, and so WSL, running. 
    -d Ubuntu-24.04 -- bash -lc "~/.venvs/ray/bin/ray start --address=<head 100.x IP> --node-ip-address=<this PC's WSL 100.x IP> --block"
    Also set Windows sleep to Never, or the node will drop out of the cluster when the PC sleeps.
How to check it worked: on any node, ray status should list one more node. The Windows PC also appears on the dashboard's Cluster page under its WSL hostname.
